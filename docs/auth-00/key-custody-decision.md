# AUTH-00 key custody decision (TOTP seeds)

Task 5097. Written decision required before any real seed migrates (plan: "Leg de keuze en sleutelcustody vast
voor echte secrets migreren"). Status: **Proposed**, to be confirmed by Martien (section 6). No real seed exists
anywhere yet; the proof of concept uses RFC 6238 test keys and throwaway random keys.

## 1. What is protected, and from whom

| Secret | Why it matters | Protected against | Not protected against |
|--------|---------------|-------------------|-----------------------|
| Seed (per item) | Permanent second factor of an external account | A copy of the database or its backups; moving a ciphertext to another row/tenant; silent modification | Someone running code inside the vault process, or an administrator of the vault host who can read the KEK |
| Data key (DEK, per item) | Opens one seed | Same as above | Same |
| Key-encryption key (KEK) | Opens every DEK | Database copy, backups, deploy artefacts, configuration files, the credential-vault `ENCRYPTION_KEY` | Host compromise with the right identity |

This is **server-side encryption**. It is not end-to-end: whoever controls the vault host and its service identity
can read seeds. Excluding the host from the trust base needs a client-side design (task 499, WebAuthn PRF
extension) and is not claimed here.

## 2. Mechanism (implemented in the PoC, `SeedProtector`)

- AES-256-GCM everywhere. A fresh random 256-bit DEK per item encrypts the seed; the KEK wraps the DEK.
- Associated data for both operations: `pm-totp-seed-v1 | purpose | tenant | owner | item | KEK version`. A
  ciphertext copied to another tenant, owner or item, or relabelled with another KEK version, fails authentication.
- Stored per item: KEK version, wrapped DEK + nonce + tag, seed nonce + tag + ciphertext. No plaintext, no key.
- Rotation: `Rewrap` moves an item to the current KEK version (new DEK, new nonces); the old KEK is retired only
  after every item reads back under the new one. Tested: rotation, retired-KEK failure, tamper and context tests.
- The existing `EncryptionService` is **not used**: AES-CBC without authentication, key derived as
  `SHA256(passphrase)` from the same configuration as the JWT key, a fixed legacy IV, no associated data (P4).

## 3. Options for where the KEK lives

| Option | Strength | Cost / risk | Verdict |
|--------|----------|-------------|---------|
| A. Environment variable or `appsettings` on the host | Separates it from the database and backups | Same place as today's `ENCRYPTION_KEY`/JWT key; readable by anything that can read config; easy to leak in deploy output | Fallback only, and only with a *separate* key value |
| **B. DPAPI (LocalMachine) protected key file outside web root and outside backup scope** | Useless on any other machine; ACL limits it to the app-pool identity; no new infrastructure | Bound to the host (restore elsewhere needs the recovery package); host admin can still read it | **Chosen for v1** |
| C. Cloud KMS / HSM (Azure Key Vault, AWS KMS, …) | Strongest separation and audit; key never leaves the service | New external dependency and cost; the host still needs a credential to call it (same bootstrap problem, smaller blast radius); network dependency in the code-release path | Revisit if the vault moves to a managed host |
| D. TPM / non-exportable CNG key | Key cannot be copied off the machine | Host TPM unknown; backup/restore of a non-exportable key is the hard part; fails closed on hardware change | Revisit with the host provider |
| E. Bitwarden (Secrets Manager or vault) as the KMS | n/a | Stores secrets, does not perform key operations; the KEK would be fetched at start-up and held in memory, i.e. option A plus a dependency; same unlocked-session problem as B1-B2 in the inventory | Rejected |

## 4. Decision

1. **KEK custody v1 = option B.** One 256-bit KEK per version, generated on the vault host, written as a
   DPAPI-`LocalMachine`-protected file at `%ProgramData%\PasswordManager\keys\totp-kek.v{n}.dpapi`, outside the web
   root and the site deploy folder, outside any database backup, ACL: the application-pool identity (read) and
   Administrators. Loaded by an `IKekProvider` implementation (`DpapiFileKekProvider`, AUTH-03); the interface is
   already in the PoC so C or D can replace B without touching the protector.
2. **Never** in `appsettings*.json`, environment variables of the credential vault, the database, the repository,
   build output, logs, ClickUp/JengoWork, prompts or agent context. The KEK is generated by a one-time command run on
   the host by a human (or by Martien's explicit go), not by an agent.
3. **Separate identity.** v1 runs in the existing vault app pool; that is the weakest link in this design and is
   stated, not hidden. The stronger shape - a tiny local "seed service" under its own Windows identity that exposes
   only `ComputeCode(grant, itemId)` over a named pipe and never returns a seed or the KEK - is the first
   risk-reduction option for AUTH-05 if the review wants it.
4. **Recovery package (offline, outside Jengo).** Created once, at KEK generation, by Martien: (a) the KEK, (b) an
   encrypted export of all items (AUTH-03 backup format: version, checksum, AES-256-GCM, key derived from a
   high-entropy passphrase with a memory-hard KDF), (c) the restore procedure. The passphrase/recovery key is held
   separately from the export. Two copies in two physical places. Neither the KEK backup nor the export is ever
   uploaded to Jengo, a mailbox or a task.
5. **Rotation.** New KEK version on a schedule (default yearly) and immediately after any suspicion of KEK exposure.
   Normal rotation is `Rewrap` of every item, verified by decrypt-and-compare of a canary item, then retire the
   old key. **If the KEK or a seed may have been exposed, rotation is not enough:** the seed is a long-lived shared
   secret, so the TOTP must be re-enrolled at each external service (plan: logging out does not invalidate a stolen seed).
6. **Prerequisites AUTH-03 must prove on the real host before the first real seed**, because they could not be
   checked from here: DPAPI `LocalMachine` works under the app pool; the key folder is excluded from the site
   deploy and from the database backup job; the ACL is as stated; a backup restore on a clean machine works using only
   the recovery package; losing the KEK file is detected (health check fails loudly, never silently regenerates).
7. **Clock.** TOTP and every TTL use the vault host clock. NTP status is monitored; a drift alarm is part of AUTH-05.
8. **Logging.** Audit lines carry actor, tenant, item id, action, time, outcome. No seed, code, grant, KEK material
   or QR payload in logs, traces, error messages, screenshots or task attachments. QR codes are never sent to an agent.

## 5. Consequences

- The PoC's `StaticKekProvider` (configuration-based, fictional keys) must not be enabled in production; the
  feature flag is off by default and the allow-list is empty.
- Bitwarden remains the user's personal manager. Nothing is imported from it automatically; the first real item is
  one GitHub test/pilot account that Martien enrols himself.
- If the vault host is ever considered untrusted, this design is insufficient by definition and the client-side
  alternative has to be designed first.
